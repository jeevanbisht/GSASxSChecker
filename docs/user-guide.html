🛡️ GSA SxS Checker v1.0

Detect WFP Driver Conflicts
with the GSA Client

A one-command PowerShell script that scans your Windows machine for security products that may conflict with the Microsoft Global Secure Access client — and generates a clear, interactive HTML report.

⬇ Download from GitHub 🚀 Quick Start

🔍 What does this tool do?

The Microsoft Global Secure Access (GSA) client uses a kernel-mode Windows Filtering Platform (WFP) driver to securely tunnel your network traffic to Microsoft Entra services. Other security or network access products may also install a WFP driver, competing for control of the same network traffic.

This is sometimes a leading cause of the GSA client failing silently — tunnels don't connect, apps that should be protected stop working, or your machine becomes unstable.

GSA SxS Checker detects these conflicting drivers in seconds and gives you a clear, actionable report — no special tools needed.

🚀 Quick Start (3 steps)

Download the script

Open PowerShell and run:

Invoke-WebRequest -Uri "https://raw.githubusercontent.com/jeevanbisht/GSASxSChecker/main/Get-GSAConflictReport.ps1" -OutFile "Get-GSAConflictReport.ps1"

Or clone the repository from GitHub.

Run as Administrator

Right-click PowerShell → Run as Administrator, navigate to the folder where you saved the script, then run: 

.\Get-GSAConflictReport.ps1

ℹ️ Running as Administrator is recommended for full WFP callout data. The script works without elevation but some sections will be empty.

Review your report

The report opens automatically in your browser. If not, open GSA-Conflict-Report.html from the same folder. Navigate the tabs to understand your machine's status.

📋 Understanding the Report

Risk Banner

The top of the report shows an overall risk level based on what was found:

NONE No conflicts detected. GSA should work normally.
LOW Minor overlap. Monitor but may be fine.
MEDIUM Known coexistence issues. Review Remediation tab.
HIGH Serious conflict. Action required. See Remediation tab.

Report Tabs

Tab 1

Summary

Machine snapshot: hostname, user, OS, GSA version, join type, and number of conflicts at a glance.

Tab 2

Findings

One card per detected conflict — vendor name, risk level, matched drivers/services, and a plain-English explanation of the issue.

Tab 3

WFP Details

Raw Windows Filtering Platform data: all active callout drivers and WFP providers. Requires Administrator. Share with your engineer when escalating.

Tab 4

Kernel Drivers

All running non-Microsoft kernel-mode drivers with publisher and digital signature information.

Tab 5

System Info

Identity (user, machine, domain, join type), OS version, hardware, GSA client services status, and network adapters.

Tab 6

Remediation

Vendor-specific step-by-step actions and PowerShell diagnostic commands you can copy and run.

❓ FAQ

Why does the script need Administrator rights?
Full WFP callout enumeration (netsh wfp show state) requires access to the Windows Filtering Platform engine, which is restricted to Administrators. Without elevation the script still runs and detects drivers via WMI, but the WFP Callouts and Providers sections of the report will be empty.
Will this script make any changes to my machine?
No. The script is read-only. It only collects data and generates an HTML report. Nothing is modified, no drivers are unloaded, and no registry changes are made.
My security software blocked the script — what should I do?
Some endpoint protection products flag unsigned PowerShell scripts. You can run it using PowerShell.exe -ExecutionPolicy Bypass -File .\Get-GSAConflictReport.ps1, or review the source on GitHub to confirm it is safe before running.
The report shows "No conflicts detected" but GSA is still not working.
The tool checks against a curated list of known conflicting products. If your issue is caused by an unlisted product, a network configuration issue, or a GSA server-side problem, it may not appear here. Check the WFP Details and Kernel Drivers tabs for any unknown drivers, and review the GSA known issues page.
Can I run this on multiple machines at once?
Yes — use Invoke-Command -ComputerName PC1,PC2 -FilePath .\Get-GSAConflictReport.ps1 -ArgumentList @{NoBrowser=$true} with PowerShell remoting, or deploy via Intune/SCCM as a detection script. Each machine generates its own report.
Can I share the report with Microsoft Support?
Yes — the report is a self-contained HTML file. Before sharing, review it for any sensitive information (IP addresses, usernames). The report does not contain passwords or secrets.
